How it works

Two agent teams at one bank. Every tool call they make goes through the AgntID runtime first.

The teams

The voice team answers the support line. The caller ID picks the customer record, so what the caller says can't change whose money it is.

What AgntID decides

We configured all three of AgntID's control levels. They feed one Runtime Access Decision per call.

Tool Access Controls

Protection Profile Medium. Tool Discovery hides export_customer_records, and hides the refund tool until a call is classified as a failed payment. Tool Execution disables raw SQL and the open-ended Slack post.

Parameter-Level Policies

query_refunds.limit 1 to 100. Refunds 1 to 5,000 rupees. refund_to_account.destination_account must be on the customer's allow-list.

Intent-Based Controls

The engineer's request, or the caller's classified need, is the task intent. Each call is checked against it, ML-based or LLM-based. Intent hasn't fired in a stand-in run yet; the stand-in can't judge intent.

The Runtime Enforcement Flow

AgntID runs these five steps for every tool call, in this order.

  1. Intent Validation. Does the call match the task? The injected export arrives inside a normal GitHub reply, so intent is judged on the call, not on the text the agent read.
  2. Policy Check. The agent sent limit=5000 to query_refunds. The policy allows 1 to 100.
  3. Scoped Access. The runtime's Credential Engine holds the GitHub token. The gated agents never see it.
  4. Execute Tool Call. Only calls that passed steps 1 to 3 reach GitHub, Postgres or Slack.
  5. Record Trace. We also write each decision to a hash-chained record signed with Ed25519.

The one layer we add

AgntID doesn't hold pending approvals, so we do. When the fix agent asks to merge, ClearGate holds the call and phones the on-call engineer. The engineer approves by saying a 4-character code. The approval is bound to the SHA-256 digest of the exact merge arguments, and ClearGate re-sends the approved call through the runtime, which makes the final decision.
