How it works

Every tool call your agent makes goes through AgntID first. ClearGate tests that, then signs the result.

  1. Run. The agent runs stock and gated on the same input.
  2. Attack. The catalogue goes in, then every blocked attack is mutated.
  3. Propose. A least-privilege policy from the calls the task needs.
  4. Gate. CI re-runs it on every PR that touches an agent or its policy.
  5. Sign. Each decision goes into a record anyone can verify.

The example teams

The examples on this site use two agent teams. Swap in your own agents and tools. The gate works the same way.

What AgntID decides

All three control levels are on. Together they make one Runtime Access Decision per call. We use seven AgntID controls. The eighth layer, digest-bound approval, is ClearGate's.

Tool Access Controls

Protection Profile Medium. Tool Discovery hides export_customer_records, and keeps the refund tool hidden until the call is a failed payment. Tool Execution disables raw SQL and the open-ended Slack post.

Parameter-Level Policies

query_refunds.limit 1 to 100. Refunds 1 to 5,000 rupees. refund_to_account.destination_account must be on the customer's allow-list.

Intent-Based Controls

The engineer's request, or the caller's need, is the task intent. AgntID checks each call against it. The local stand-in can't judge intent, so these checks run only on the live runtime.

The Runtime Enforcement Flow

Five steps, in order, for every tool call.

  1. Intent Validation. Does the call match the task? The injected export arrives inside a normal GitHub reply, so AgntID judges the call itself.
  2. Policy Check. The agent sent limit=5000 to query_refunds. The policy allows 1 to 100.
  3. Scoped Access. The runtime's Credential Engine holds the GitHub token. The gated agents never see it.
  4. Execute Tool Call. Only calls that passed steps 1 to 3 reach GitHub, Postgres or Slack.
  5. Record Trace. ClearGate also signs each decision into a hash-chained record (Ed25519).

What AgntID does vs what ClearGate adds

AgntID enforces. ClearGate tests that enforcement before go-live and signs the result. The left column uses AgntID's own terms. ClearGate never edits the portal configuration.

The one enforcement layer we add

AgntID doesn't hold pending approvals, so ClearGate does. When the fix agent asks to merge, ClearGate phones the on-call engineer, who approves by saying a 4-character code. The approval is bound to the SHA-256 digest of the exact merge arguments. The approved call still goes back through AgntID.
